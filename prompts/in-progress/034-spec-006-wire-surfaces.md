# Resolve every scope value on both surfaces

<summary>
- A URL naming two scopes returns results drawn from both of them, on the REST routes and on the MCP mount
- The two surfaces can no longer disagree: both resolve scope through one shared function, on every value the URL carries
- The order the scopes are named in does not change the result set
- A request naming an undeclared scope is refused whole with the existing 400 and token, and serves no results
- The offending value is named in the refusal's log line, because the response body is frozen to the token
- A request naming a single scope returns byte-identical results — same paths, same order, same scores
- The bracket form and the comma form stay refused, exactly as they are today
- No surface extracts a single scope value any more; the resolver is invoked from all four call sites
- The response envelopes, the error tokens, the index build and the embedding path are untouched
- A changelog entry records the union capability
</summary>

<objective>
Wire both HTTP surfaces to the multi-value resolver so a repeated `?scope=` searches the union of the named scopes' roots on the REST routes and on the MCP mount alike, an undeclared name fails the whole request closed, and a single-scope request keeps returning byte-identical results. This closes the divergence the spec measured — the same URL returning Personal on `/search` and Brogrammers on `/mcp` — and delivers the capability the operator asked for: one session spanning several scopes.
</objective>

**Verified facts you can rely on (re-measured on this tree):**

- `starlette.requests.QueryParams.getlist("scope")` returns a `list[str]` — `[]` when the parameter is absent, and it keeps blank entries (`?scope=&scope=personal` gives `["", "personal"]`). `QueryParams.get("scope")` returns the **last** value; `parse_qs(...).get("scope", [None])[0]` returns the **first**. That is exactly the divergence this prompt closes.
- `urllib.parse.parse_qs` drops blank values, so the middleware's `["personal"]` and Starlette's `["", "personal"]` reach the resolver as the same request once blank values are ignored — the two surfaces agree on that query string either way.
- The middleware's current extraction is wrapped across three lines by the formatter, so the literal `[0]` subscript sits on its own line: the stable searchable fragment is `.get("scope", [None])`.
- The `?scope[]=` form is not a `scope` parameter at all — Starlette parses the key as `scope[]`, so `getlist("scope")` is empty and the request is refused as missing. The `?scope=a,b` form arrives as the single value `"a,b"`, which the resolver rejects as an unknown name. Both stay refused without any code being written for them.
- An unknown *parameter* (for example `?scope=personal&bogus`) is ignored: it is not a `scope` value, so the request is served normally. The repeated form is what makes an unknown name observable.
- The index directory is keyed on the joined resolved roots (`paths_str = ",".join(str(p.resolve()) for p in self.vault_paths)` → `content_hash` → `index_dir` in `indexer.py`), so an index built over two roots and one built over a single root cannot share a cache entry.
